# Инструкции, навыки и агенты

Эти механизмы решают разные задачи. Если смешивать их в одном большом системном промпте, инструкции становятся труднее поддерживать, а ненужный контекст загружается в каждый запрос.

## Краткий выбор

| Механизм | Для чего | Пример |
|---|---|---|
| **Обычный промпт** | Разовая цель и контекст одной задачи | «Объясни эту функцию и найди вызывающие её места» |
| **Постоянная инструкция** | Простые правила, нужные в большинстве задач | Язык, соглашения проекта, команды тестирования |
| **Путь-специфичная инструкция** | Правила для определённых файлов или подсистем | Правила для `Tests/**/*.cs` |
| **Skill** | Переиспользуемый редкий процесс с контекстом, примерами или файлами | Процедура ревью учебной заметки |
| **Custom agent** | Специализированная функция, с отдельными задачами, инструкциями и, в некоторых системах, правами | Исследователь только для чтения; тестовый арбитр |
| **Tool / MCP** | Новая операция или доступ к внешнему ресурсу | Получить issue или создать календарное событие |
| **Hook** | Код, выполняемый при определённом событии workflow | Проверить путь до вызова инструмента |

Названия и поддержку проверяй для конкретного продукта. В Copilot CLI это отдельные понятия, подробно описанные в официальной таблице сравнения; другие IDE, cloud agents или LLM-платформы могут использовать те же термины по-разному.

## Принципы хорошей постоянной инструкции

1. Пиши правила, которые действительно нужны часто; узкую процедуру перенеси в skill.
2. Формулируй действия и исключения конкретно: «после изменения C++ запусти тест X» полезнее, чем «пиши качественный код».
3. Добавляй только проверенную информацию о проекте и актуальные пути/команды.
4. Убирай дубли и противоречия между пользовательскими, глобальными, проектными и файловыми инструкциями.
5. Не превращай инструкцию в журнал прошлых задач или в каталог всего репозитория.
6. Перепроверяй, какие поверхности продукта загружают данный файл.

## Проектирование skill

Skill уместен, если задача повторяема, но нужна только в некоторых случаях. Он может включать инструкцию, дополнительные материалы и скрипты.

Хороший `SKILL.md` обычно содержит:

1. **Метаданные** — точное имя и короткое описание с ясными сигналами вызова.
2. **Назначение и границы** — что делает skill, что не делает и когда его не вызывать.
3. **Входы и подготовка** — какие файлы/ресурсы прочитать, какие предпосылки проверить.
4. **Шаги** — небольшой упорядоченный процесс с развилками по реальным условиям.
5. **Критерии готовности** — как проверить итог.
6. **Формат результата** — что вернуть пользователю и как указать незавершённые проверки.
7. **Ссылки на локальные материалы** — примеры, схемы, скрипты; держать длинные справочники в отдельных файлах.

Набросок для Copilot CLI:

```markdown
---
name: note-review
description: Проверяет русскоязычные заметки базы знаний на структуру, точность
  и ссылки. Используй после создания или существенной переработки заметки.
---

1. Прочитай заметку и только нужные связанные заметки.
2. Проверь структуру по чек-листу в `review-checklist.md`.
3. Сверь технические утверждения с указанными первоисточниками.
4. Раздели подтверждённые дефекты, рекомендации и неизвестное.
5. Верни файл/раздел, доказательство и рекомендуемое исправление.
Не изменяй заметку, если пользователь просил только ревью.
```

Описание должно быть точным и отличимым от соседних навыков: автоматический выбор зависит от того, насколько описание соответствует текущей задаче, и не гарантируется. Если skill содержит скрипты, проверь их до использования. Особенно опасно заранее разрешать `shell`/`bash`: это снимает подтверждение команд и может дать вредоносному содержимому выполнить действия в окружении. Не добавляй `allowed-tools` без проверенной необходимости и анализа риска.

## Проектирование custom agent

Agent-профиль подходит для повторяемой специализированной работы, когда нужны отдельные инструкции, стиль анализа или ограничения доступных инструментов.

В профиле явно укажи:

- **идентификатор и описание:** экспертиза и ситуации вызова;
- **задачу:** точный класс работ и остановочные условия;
- **процедуру:** в каком порядке исследовать и проверять;
- **разрешённые инструменты и источники:** минимальный набор;
- **границы:** запрещённые изменения и действия, требующие согласия;
- **формат отчёта:** выводы, доказательства, файлы, неопределённость.

Ограничение инструментов имеет смысл: например, аудитор, которому нужно только читать, обычно не нуждается в записи файлов. Но read-only не гарантирует отсутствие ошибочных выводов и не заменяет ручную проверку. Даже профиль с именем «эксперт» не доказывает наличие у модели человеческой квалификации.

Для участника коллегии задай внутренне согласованную область, например: «оценить корректность тестовых вопросов по связанным источникам; не проверять ответы пользователя; отдельно сообщить дефекты теста, заметки и неопределённость». Отдельного арбитра снабди рубрикой и попроси независимый вывод, а не подтверждение мнения автора.

Ролевая метка «стажёр» или «senior» не меняет автоматически знаний модели; prompt не может надёжно стереть знания, полученные при обучении. Можно ограничить разрешённые источники, попросить не использовать внешние сведения и требовать привязки выводов к заметке, но это не даёт абсолютной гарантии. Поэтому ученик-новичок должен обосновывать ответы содержимым заметки, а неподтверждённые сведения отмечаются; агент с ролью опытного разработчика полезен для сложных сценариев и технической критики, но не заменяет читателя-новичка.

## Раздача задачи субагентам

Делегируй только независимый подрезультат, который можно проверить отдельно:

```text
Цель:
Изучить официальную документацию GitHub Copilot CLI по skills.

Доступный корпус:
Официальная документация GitHub и встроенная справка CLI; не редактируй файлы.

Нужно вернуть:
5–8 подтверждённых рекомендаций, точные URL, дату доступа и ограничения.

Не делать:
Не переносить правила IDE/cloud agent на CLI без подтверждения.
Не выдавать предположения за факты; отметить любой недоступный источник.
```

Для нескольких агентов разделяй независимые исследовательские углы или проси отдельные оценки. Не используй видимость «консенсуса» как доказательство, если агенты видели выводы друг друга или разделяют общий неверный источник. Родительский агент отвечает за синтез, проверку конфликтов и финальные критерии.

## Когда агент не нужен

Не создавай агента ради одиночного вопроса, известного файла, простой правки или фиксированного процесса, который легче и надёжнее написать явным кодом. Если LLM только выполняет линейные этапы A→B→C, workflow с проверками может быть предсказуемее автономного агента. Агентность уместна, когда модели действительно нужно выбирать следующий шаг или инструмент из меняющегося состояния и выгода оправдывает стоимость, задержку и риск.

## Версионирование и обслуживание

- Пиши дату ревизии и целевой продукт/поверхность для продуктовых инструкций.
- Проверяй skill/agent на типовых запросах и на ошибочных сигналах, которые не должны его запускать.
- Удаляй дубли, устаревшие примеры и лишние разрешения.
- Храни изменения в Git; сравнивай их с исходной версией и повторяй eval при изменении текста, модели или инструментов.
- Для Copilot CLI после добавления/обновления skill используй поддерживаемый способ перезагрузки и проверь, что он доступен; для агентов проверь фактический список и профили в текущей версии.
