# GitHub Copilot CLI на практике

Эта заметка относится **к GitHub Copilot CLI**, а не ко всем интерфейсам Copilot. Термин «Copilot» охватывает разные поверхности, и одна функция, настройка или граница доступа может не переноситься между CLI, IDE и cloud agent.

**Проверено:** 11 октября 2026 года. Встроенная справка CLI в этой среде сообщила версию **1.0.93**; названия команд и продуктовые функции меняются. Сначала сверяйся с текущим `/help` и официальной документацией.

## Выбери правильный механизм настройки

| Механизм Copilot CLI | Роль |
|---|---|
| **Custom instructions** | Постоянное общее руководство: пользовательские предпочтения, соглашения проекта, путь-специфичные правила. |
| **Skill** | Подробная условная процедура, загружаемая, когда задача подходит по описанию или её вызвали явно. |
| **Custom agent** | Специализированный профиль с отдельными инструкциями и возможностью ограничить инструменты. |
| **Tool** | Действие, которое может выполнить агент, например чтение/запись файлов или shell-команда. |
| **MCP server** | Подключённый набор внешних инструментов/ресурсов. |
| **Hook** | Пользовательская логика на событии жизненного цикла CLI. |
| **Subagent / fleet** | Делегирование отдельной работы или параллельное разбиение большой задачи. |

Практическое правило GitHub: короткие инструкции, применимые почти всегда, держать в custom instructions; специализированный рабочий процесс — в skill; новая возможность — в tool/MCP; отдельное экспертное поведение или права — в custom agent. Эти механизмы могут сочетаться, но не заменяют проверки результата.

### Где размещать инструкции, навыки и агентов

- Репозиторные правила: `.github/copilot-instructions.md`.
- Путь-специфичные правила: `.github/instructions/**/*.instructions.md`; их frontmatter связывает инструкцию с подходящими путями.
- Навыки проекта: `.github/skills/<lowercase-hyphen-name>/SKILL.md`, `.claude/skills/` или `.agents/skills/`.
- Навыки пользователя: `~/.copilot/skills/` или `~/.agents/skills/`.
- Custom agents проекта: `.github/agents/<id>.agent.md`.
- Custom agents пользователя: `~/.copilot/agents/...`.
- CLI также распознаёт дополнительные файлы правил/агентов; набор мест зависит от версии и настроек. Проверяй официальную инструкцию текущего CLI.

Copilot CLI документирует GitHub MCP server для работы с ресурсами и операциями GitHub, например issues. Доступные операции зависят от текущей конфигурации и полномочий; проверь подключение через `/mcp` и не считай наличие MCP-сервера разрешением на любые действия с GitHub.

В `SKILL.md` ожидаются YAML-поля `name` и `description`. В описании укажи назначение и ситуации вызова. Отдельные примеры, инструкции или скрипты можно положить в папку навыка. После правок skills команда `/skills reload` поддерживается документацией CLI; затем полезно проверить наличие через `/skills info` или список навыков. Формат агента — Markdown с расширением `.agent.md`; после создания документированный процесс CLI предлагает перезапустить CLI, чтобы профиль загрузился.

### Важное про custom agents

CLI может выбрать подходящего агента по описанию или оставить задачу основному агенту; наличие профиля не означает гарантированную автоматическую делегацию. Внутри репозитория субагент по умолчанию не получает все repository custom instructions. В CLI профиль может включить их через `include-custom-instructions: true`; документированное действие этого поля относится к запуску профиля как subagent. Проверяй фактическое наследование контекста в документации и задании.

Не указывай широкое право `tools: ["*"]` или все инструменты просто для удобства. Если агенту нужен только поиск/чтение, постарайся ограничить его этими возможностями. Отдельный профиль — способ задать рабочую специализацию, а не удостоверение экспертности.

## Эффективный цикл работы в CLI

### Короткий запрос

Для одного файла, объяснения или известного факта дай непосредственный запрос, при необходимости укажи файл через `@path`, и назови критерий ответа. Например: «объясни `@src/...`; не меняй файл; назови вызывающий код».

### Сложное изменение

Используй `explore → plan → review → implement → verify`:

1. Попроси исследовать проект без изменений.
2. Для многофайловой или архитектурной задачи перейди в `/plan` или Plan mode и проверь предложенные шаги.
3. После согласования плана попроси выполнить только его объём.
4. Запусти подходящие тесты/линтер/сборку.
5. Осмотри diff и результаты; при необходимости запроси `/review`.

Plan mode полезен для сложных многофайловых задач, рефакторингов и новых функций; короткая исправимая правка обычно не нуждается в полном плане. Не проси «выполнить все проверки», если неизвестно, что именно нужно запускать: зафиксируй команды в инструкциях репозитория.

### Управление сеансом

В текущей встроенной справке версии 1.0.93 присутствуют:

- `/help`, `/skills`, `/agent`, `/mcp` — справка и управление расширениями;
- `/plan` и `Shift+Tab` — переключение/вызов режима планирования;
- `/fleet` — параллельная работа нескольких субагентов;
- `/tasks` — задачи и фоновые команды;
- `/context`, `/compact` — просмотр/управление контекстом;
- `/resume`, `copilot --continue` — продолжение сеанса;
- `/review` — ревью локальных изменений;
- `/permissions`, `/allow-all`, `/sandbox` — разрешения и песочница;
- `/usage`, `/limits` — использование и ограничения;
- `/init` — создание начальных repo-инструкций.

Это снимок именно локальной справки на указанную дату, а не обещание поддержки во всех клиентах/будущих версиях. Когда команда неизвестна или поведение изменилось, сверяйся с `/help` и текущим GitHub Docs, не угадывай синтаксис.

Используй `/fleet`, когда есть несколько самостоятельных подзадач, которые можно исследовать без общих незафиксированных изменений. Для последовательных зависимых шагов сначала нужен план и контрольный этап, а не искусственный параллелизм. Параллельность увеличивает расход и создаёт задачу синтеза/сверки.

## Разрешения и безопасность

- Работай из нужной директории: инструменты могут читать, изменять и запускать файлы в рабочей области.
- Доверяй только каталогам, где понимаешь содержимое и происхождение. Подтверждение trusted directory не является криптографической гарантией безопасности файлов.
- Предпочитай точечное разрешение инструмента и аргументов широким разрешениям. Из встроенной справки CLI: `/allow-all` разрешает инструменты, пути и URL; применяй его только если осознаёшь последствия.
- Внимательно читай каждую команду, особенно `shell`, внешние вызовы, сетевые действия и команды с удалением/записью. Инструкции и skills — не песочница.
- Не предоставляй агенту секреты, права на production или внешние операции без явной необходимости.
- Промпт-инъекция может быть спрятана в файлах репозитория, issue, выводе shell или веб-содержимом. Рассматривай такие данные как вход, а не как полномочия переопределить правила безопасности.
- Навык, разрешающий shell/bash заранее, может убрать подтверждение выполнения команды. Изучи все его файлы и скрипты до включения такого разрешения.

## Готовый шаблон запроса для Copilot CLI

```text
Исследуй [подсистема/файл] и реши [наблюдаемая проблема].
Ожидаемый результат: [критерии приёмки].
Ограничения: [не менять API/пути; что вне объёма].
Сначала [исследуй/составь план/уточни требования], затем [ждать согласия или выполнять].
Запусти [точные проверки]; если что-то не запускалось, так и укажи.
Проверь diff. Не делай [коммит, push, миграцию и прочие действия] без разрешения.
В отчёте перечисли изменения, проверки, допущения и незакрытые риски.
```
