# UFUNCTION в Unreal Engine: спецификаторы, meta и RPC

`UFUNCTION` описывает метод для системы отражения Unreal Engine. Он позволяет Blueprint вызывать C++-логику, задавать переопределяемое поведение, связывать динамические события и создавать RPC. Сам макрос не заменяет реализацию метода.

**Основная мысль:** отдельно выбирать способ вызова, возможность переопределения, сетевую сторону выполнения и оформление Blueprint-узла. Эти задачи не решаются одним универсальным `BlueprintCallable`.

Материал рассчитан на UE 5.8 и базовое знание C++. Для первого чтения — разделы 1–6 и 10; разделы 7–9 — справочник ключей.

## 1. UFUNCTION и обычный метод C++

Для вызова одного C++-метода из другого `UFUNCTION` не обязателен. Обычный метод подходит, если ему не нужны отражение, Blueprint, RPC или другой механизм, который требует отражаемую функцию.

Пример объявления в UObject-классе:

```cpp
/** Показывает локальное сообщение UI; сетевую доставку организует вызывающий код. */
UFUNCTION(BlueprintCallable, Category = "UI|Notification")
void ShowMessage(const FText& Text, float Duration = 2.0f);
```

Тело обычного нативного метода пишется в `.cpp` под исходным именем `ShowMessage`. Для этой формы не нужна функция с суффиксом `_Implementation`.

**UHT** (Unreal Header Tool) разбирает объявление и генерирует описание функции и необходимые точки входа для отражения. `UFUNCTION()` без аргументов отражает метод, но не открывает его как вызываемый Blueprint-узел автоматически.

Макрос применяют к поддерживаемым методам UObject-классов и отражаемых интерфейсов. Не добавлять его к произвольной свободной функции или методу USTRUCT. Обычные методы структуры можно оставить обычными C++-методами.

Все фрагменты в статье — отдельные учебные объявления, не готовый модуль. Нужны соответствующий UCLASS, GENERATED_BODY, инклюды и реализация. Они проверены чтением первоисточников и по безопасности, но не компилировались как самостоятельный проект.

## 2. Четыре независимых слоя объявления

| Слой | Примеры | Что определяет |
|---|---|---|
| Обычный C++ | `public`, `protected`, `private`, `const`, `static`, `virtual` | Доступ, принадлежность и семантику C++-метода |
| Спецификаторы UFUNCTION | `BlueprintCallable`, `BlueprintNativeEvent`, `Server` | Способ участия функции в механизмах Unreal |
| Функциональные meta | `WorldContext`, `Latent`, `AutoCreateRefTerm` | Дополнительную работу поддерживающих их Blueprint-инструментов |
| Оформление узла | `DisplayName`, `CompactNodeTitle`, `AdvancedDisplay` | Представление и удобство использования в графе |

`meta` — не только косметика: по нему компилятор Blueprint может подготовить специальный узел. Но игровая логика не должна рассчитывать на чтение редакторских метаданных в packaged build или использовать их вместо runtime-проверок.

Доступность из Blueprint и доступность из C++ — разные вопросы. `BlueprintProtected` не заменяет ключевое слово `protected`. И `public` сам по себе не создаёт Blueprint-узел.

## 3. BlueprintCallable, BlueprintPure и const

### BlueprintCallable: действие с порядком выполнения

Обычно callable-узел имеет вход и выход **Exec** — контакты, задающие порядок выполнения в графе. Подходит для действий: показать окно, изменить состояние, отправить команду.

`BlueprintCallable` не гарантирует, что вызов разрешён по игровым правилам. Проверки параметров, состояния и сетевой стороны находятся в реализации.

### BlueprintPure: вычисление результата

```cpp
/** Читает локальное состояние UI, ничего не изменяя. */
UFUNCTION(BlueprintPure, Category = "UI|Notification")
bool IsMessageActive() const;
```

Pure-узел не имеет обычной Exec-цепочки и вычисляет данные для потребителей результата. Внутри него не следует выполнять игровые действия или менять состояние.

**Pure не означает «автоматически быстро, потокобезопасно или закэшировано».** Не рассчитывать, что дорогой поиск или загрузка ассета в pure-узле выполнятся ровно один раз: вычисления могут повторяться в зависимости от графа и потребителей. Для дорогостоящего результата можно использовать явное действие и сохранение результата.

UHT требует у pure-функции возвращаемое значение или выходной параметр. Пометка pure на `void`-методе без outputs отвергается.

### Почему const-метод иногда становится pure

`const` в C++ означает ограничения на изменение самого объекта через этот метод, но не математическую чистоту и не отсутствие всех побочных эффектов.

В проверенном UHT `const BlueprintCallable` с выходным значением/параметром может автоматически получить BlueprintPure. Чтобы сохранить Exec-порядок:

```cpp
/** Формирует локальный UI-предпросмотр; вызывается с явным Exec-порядком. */
UFUNCTION(BlueprintCallable, BlueprintPure = false, Category = "UI|Notification")
FText BuildPreviewText() const;
```

`BlueprintPure = false` не отменяет `const`. Оно управляет представлением функции в Blueprint и отключает автоматическую pure-пометку. Не объединять его с `BlueprintPure` или `BlueprintPure = true`.

## 4. Blueprint-события: где находится реализация

### BlueprintImplementableEvent

```cpp
/** Локальное событие UI; поведение задаёт дочерний Blueprint. */
UFUNCTION(BlueprintImplementableEvent, Category = "UI|Notification")
void OnMessageShown(const FText& Text);
```

Это точка расширения, которую реализуют в Blueprint. Не писать для неё обычное C++-тело `OnMessageShown` или `_Implementation`: инфраструктуру вызова создаёт UHT.

C++ вызывает `OnMessageShown(Text)`, а движок передаёт вызов Blueprint-реализации, если она есть. Не помещать обязательную игровую операцию только в такое событие, если допустимо отсутствие реализации.

### BlueprintNativeEvent

Нужен, когда предусмотрена нативная реализация по умолчанию и возможность переопределить её в Blueprint:

```cpp
/** Возвращает текст локального UI; допускает Blueprint-переопределение. */
UFUNCTION(BlueprintNativeEvent, Category = "UI|Notification")
FText GetDisplayText() const;

/** Нативная реализация локального UI, используемая без Blueprint-переопределения. */
virtual FText GetDisplayText_Implementation() const;
```

Пример тела в `.cpp` условного `UExampleWidget`, где есть поле `FText Message`:

```cpp
FText UExampleWidget::GetDisplayText_Implementation() const
{
    return Message;
}
```

В обычном вызывающем коде использовать **`GetDisplayText()`**, не `GetDisplayText_Implementation()`: исходное имя сохраняет маршрутизацию в Blueprint. Прямой вызов `_Implementation` обходит Blueprint-переопределение.

Дочерний Blueprint, переопределивший событие, не обязан автоматически выполнять нативного родителя. Для сохранения родительского поведения нужен соответствующий вызов Parent. В C++ переопределяют виртуальную `_Implementation` и вызывают `Super::..._Implementation()`, если требуется родительская логика.

### Event — не обязательно узел Event Graph

Метод с возвращаемым значением обычно реализуется в Blueprint как функция. Для поддерживаемого события без результата `meta = (ForceAsFunction)` позволяет представить его как переопределяемую функцию вместо обычного event-узла.

Вызов из C++ и реализация в Blueprint — не то же самое, что доступность вызова из графа. Если Blueprint должен также вызывать метод как обычный узел, нужно явно продумать `BlueprintCallable`.

Не объединять `BlueprintImplementableEvent` и `BlueprintNativeEvent`. В проверенном UHT такие события не могут быть приватными и не сочетаются с RPC-спецификаторами. Blueprint Custom Event с сетевыми настройками — другой механизм, не основание ставить `Server` на C++ BlueprintNativeEvent.

## 5. RPC: вызов, который выполняется на другой стороне

**RPC** (Remote Procedure Call) — удалённый вызов. Его направление определяет не имя метода, а сетевые спецификаторы и состояние объекта/соединения.

| Направление | Типичный сценарий |
|---|---|
| `Server` | Владеющий клиент отправляет серверу намерение выполнить игровое действие |
| `Client` | Сервер сообщает результат клиенту-владельцу объекта |
| `NetMulticast` | Сервер инициирует событие на себе и клиентах, для которых объект релевантен |
| `Remote` | Вызов выполняется на другой стороне соединения для объекта, принадлежащего клиенту |

### Объявление и реализация

В подходящем реплицируемом Actor/PlayerController:

```cpp
/** Клиент-владелец запрашивает взаимодействие; проверка и действие выполняются на сервере. */
UFUNCTION(Server, Reliable)
void Server_RequestInteraction(AActor* Target);

/** Вызывается сервером; локальную подсказку показывает клиент-владелец. */
UFUNCTION(Client, Unreliable)
void Client_ShowMessage(const FText& Text);
```

Тела пишутся в `Server_RequestInteraction_Implementation` и `Client_ShowMessage_Implementation`. Вызывают исходные имена, не `_Implementation`: иначе обходят сетевую маршрутизацию.

Ни одно объявление само по себе не гарантирует работоспособную сеть. Нужны репликация объекта/компонента, корректное сетевое владение и поддерживаемые параметры. Обычный UUserWidget не превращается в сетевой Actor от добавления UFUNCTION.

RPC не возвращает результат синхронно вызывающему клиенту: у него нет обычного return-значения. Для результата используют отдельный ответ, реплицируемое состояние или другой предусмотренный механизм.

### Владение и важные исключения

- Server RPC с клиента работает по объекту с подходящим owning connection. Вызов на чужом или не принадлежащем соединению объекте не является способом получить доступ к серверу.
- Client RPC, вызванный на сервере для клиентского владельца, направляется этому владельцу, не всем игрокам.
- Вызов Client RPC с клиента не отправляет уведомление другому клиенту: в обычной матрице исполнения он выполняется локально на вызывающем клиенте.
- NetMulticast с сервера выполняется на сервере и релевантных клиентах. Вызов с клиента остаётся локальным, а не распространяется по сети.
- Remote предназначен для клиентского владения и не выполняется на вызывающей локальной стороне; без подходящего соединения вызов может отбрасываться. Это не сочетание «дописать Client и Server одновременно».

Поведение listen host, локального владельца и отсутствия соединения нужно проверять отдельно. Префиксы `Server_`, `Client_`, `Multicast_` помогают читать код, но не создают сетевой семантики.

### Reliable и Unreliable

`Reliable` обеспечивает повторную отправку и подтверждение в рамках работающего соединения/канала и соответствующие гарантии порядка. Это дополнительная цена по очередям и трафику, а не «всегда мгновенно и при любых разрывах».

`Unreliable` допускает потерю сообщения. Подходит для части кратковременных косметических событий, если потеря допустима. Постоянное важное состояние не стоит хранить только в таких событиях.

В проверенном C++ UHT для обычного RPC нужно явно выбрать **одно**: `Reliable` или `Unreliable`. Нельзя поставить оба или использовать их на обычной несетевой функции. В документации встречается общий тезис «RPC unreliable по умолчанию», но он не отменяет требований конкретного UHT к C++-объявлению.

Не отправлять Reliable RPC каждый кадр без необходимости. Надёжность доставки не заменяет серверные проверки и ограничение частоты запросов.

### WithValidation

```cpp
/** Запрос клиентского владельца; отдельная проверка протокольной допустимости выполняется сервером. */
UFUNCTION(Server, Reliable, WithValidation)
void Server_RequestInteractionValidated(AActor* Target);
```

Для этой формы нужны `_Implementation` и `_Validate`. Validation-функция принимает соответствующие параметры и возвращает bool. При удалённом вызове проверка выполняется перед реализацией.

**Возврат false из `_Validate` может привести к отключению вызывающего клиента.** Не использовать это как обычный способ сообщить «нет места», «слишком далеко» или другую ожидаемую игровую неудачу. Такие отказы обрабатываются серверной игровой логикой без обязательного разрыва соединения.

WithValidation не является готовой проверкой безопасности. Нужно самостоятельно проверять Target, допустимость действия, полномочия, актуальное состояние и частоту вызовов. Без WithValidation эти проверки всё равно необходимы. Не полагаться на вызов `_Validate` как на единственное место проверки при любых локальных путях вызова.

## 6. Параметры, UPARAM, ссылки и Blueprint-пины

**Пин** — вход/выход узла Blueprint. Его направление определяется отражаемой сигнатурой, а не только тем, как C++-разработчик мысленно использует аргумент.

### Вход, выход и ref

| C++-параметр | Типичное представление в Blueprint |
|---|---|
| `float Duration` | Вход по значению |
| `const FText& Text` | Вход; C++ не изменяет переданный текст |
| `TArray<int32>& Values` | Неконстантная ссылка обычно становится выходным параметром |
| `UPARAM(ref) TArray<int32>& Values` | Явная входная reference-семантика для Blueprint |

```cpp
/** Изменяет переданный локальный массив; не выполняет сетевых действий. */
UFUNCTION(BlueprintCallable, Category = "Utilities")
static void UpdateValues(UPARAM(ref) TArray<int32>& Values);
```

`UPARAM(ref)` не добавляет `const` и не делает массив неизменяемым: C++-функция всё ещё может менять переданное значение. Оно управляет отражаемым представлением параметра.

У возвращаемого значения появляется выходной пин результата. Для outputs можно использовать поддерживаемые параметры по ссылке. Не переносить эту модель на RPC как способ синхронно вернуть данные через сеть.

### AutoCreateRefTerm

```cpp
/** Читает локальный массив; неподключённый вход может получить пустое значение от Blueprint-компилятора. */
UFUNCTION(BlueprintCallable, Category = "Utilities",
          meta = (AutoCreateRefTerm = "Values"))
static void InspectValues(const TArray<int32>& Values);
```

Метаданные позволяют подготовить значение для неподключённого reference-пина вместо обязательного подключения. Это не механизм определения «аргумент не передали», не разрешение хранить ссылку после завершения вызова и не изменение правил C++-вызова.

Правильное написание — **`AutoCreateRefTerm`**. Встречающееся в отдельных веб-таблицах `AutoCreateRef` не является этим же ключом.

### Имя параметра и DisplayName

Имя пина можно настроить через `UPARAM(DisplayName = "Message")` перед параметром, например перед `const FText& Text`. Имена внутри `meta = (AdvancedDisplay = "Duration")` или `WorldContext = "WorldContextObject"` должны ссылаться на **C++-имена параметров**, не на их новые подписи.

Доступные в локальном `UhtPropertyArgumentSpecifiers.cs` специализированные обработчики: `ref`, `Const`, `NotReplicated`, `Required`, `Verse`. Из них `ref` наиболее полезен в обычном API. `Const` задаёт отражаемый const-флаг; обычно яснее писать реальный `const` в C++. `NotReplicated` для параметра относится к специальным ServiceRequest, не к обычному RPC или любому аргументу. `Required` и `Verse` — специализированные механизмы, не универсальный способ валидации входа.

## 7. Справочник спецификаторов UFUNCTION

Перечислены все **22 специализированных обработчика** из локального `UhtFunctionSpecifiers.cs`, плюс общеупотребимые общие записи. Это перечень установленной версии исходников, а не неизменный список для будущих версий.

### Blueprint и доступ

| Ключ | Назначение и ограничение |
|---|---|
| `BlueprintCallable` | Вызов из Blueprint |
| `BlueprintPure`, `BlueprintPure=true/false` | Pure-узел или явное отключение автоматического pure |
| `BlueprintImplementableEvent` | Реализация в Blueprint |
| `BlueprintNativeEvent` | Нативная реализация с Blueprint-переопределением |
| `BlueprintGetter` | Отражаемый getter связанного UPROPERTY; подразумевает callable/pure |
| `BlueprintSetter` | Отражаемый setter связанного UPROPERTY; подразумевает callable |
| `BlueprintAuthorityOnly` | Authority-ограничение вызова из Blueprint; не отправка RPC |
| `BlueprintCosmetic` | Косметическая функция, не предназначенная для исполнения на dedicated server в соответствующем Blueprint-пути |
| `Category="UI\|Notification"` | Категория Blueprint-функции |
| `meta=(...)` | Дополнительные ключи для инструментов |

`BlueprintAuthorityOnly` не переносит выполнение с клиента на сервер. `BlueprintCosmetic` не рассылает эффект клиентам и не означает «только один нужный игрок». Обычный прямой нативный C++-вызов не следует считать автоматически защищённым этими Blueprint-ограничениями: требуемые проверки стороны остаются в коде.

### RPC

| Ключ | Назначение и ограничение |
|---|---|
| `Server` | RPC на сервер |
| `Client` | RPC к клиенту-владельцу |
| `NetMulticast` | RPC с серверной рассылкой релевантным клиентам |
| `Remote` | RPC на удалённую сторону подходящего клиентского соединения |
| `Reliable` | Надёжная отправка в рамках поддерживаемого канала |
| `Unreliable` | Отправка с допустимой потерей |
| `WithValidation` | Подготовка отдельной validation-функции |

Обработчики `Client`, `Server`, `Remote` допускают специальную форму с именем нативной реализации, а WithValidation — с именем проверки. Для обычного кода предпочтительны привычные формы и `_Implementation`/`_Validate`, а не редкие варианты переименования.

### Редактор, консоль и специальные механизмы

| Ключ | Назначение и ограничение |
|---|---|
| `CallInEditor` | Общая запись для действия из редактора/Details там, где оно поддерживается |
| `Exec` | Консольная команда в поддерживаемой цепочке обработки Exec |
| `CustomThunk` | Собственная обработка входа из Blueprint VM вместо стандартного сгенерированного thunk |
| `SealedEvent` | Запрет соответствующего переопределения для поддерживаемого event; не общий аналог final |
| `FieldNotify` | Функция-источник значения для системы уведомлений/MVVM |
| `ServiceRequest` | Специальная сервисная сетевая инфраструктура с endpoint/идентификаторами |
| `ServiceResponse` | Ответ в этой инфраструктуре |
| `Verse` | Специальная интеграция с Verse |

**Thunk** — промежуточная точка входа, которая преобразует отражаемый/Blueprint-вызов в нативную реализацию. `CustomThunk` требует собственной корректной обработки параметров, например через `DECLARE_FUNCTION`; не добавлять его только ради «гибкого типа».

Для FieldNotify проверенный UHT требует функцию без входных параметров, с результатом, pure и не Blueprint-event. Также нужна соответствующая инфраструктура класса; слово FieldNotify не создаёт полноценную MVVM-систему.

SealedEvent разрешён только на поддерживаемых событиях; проверенный UHT отвергает его у Blueprint-событий. Не копировать старую рекомендацию «закрыть BlueprintNativeEvent с помощью SealedEvent» без сверки версии. Для обычного виртуального C++-метода существует `final`, но это другой слой.

ServiceRequest/ServiceResponse требуют endpoint и своей инфраструктуры, получают специальные сетевые флаги. Это не готовый HTTP/backend API.

Обработчик Verse принимает специальные опции, включая `native_callable`, `verse_callable`, `decides`, `no_rollback`, `rtfm_always_open`, `extension_method`, `name`. Они перечислены для полноты исходников, не как настройки обычного UI.

## 8. Справочник функциональных meta

**Закрытого списка всех meta нет:** его расширяют движок, конкретные Blueprint-узлы и плагины. Общий парсер UHT принимает пары ключ–значение, но наличие ключа не гарантирует, что его кто-то использует.

### Подпись и удобство узла

| Ключ | Назначение |
|---|---|
| `DisplayName="..."` | Заголовок узла |
| `CompactNodeTitle="..."` | Компактное представление и его заголовок |
| `Keywords="..."` | Дополнительные слова поиска узла |
| `ToolTip="..."`, `ShortToolTip="..."` | Подсказки в поддерживающих их инструментах |
| `ReturnDisplayName="..."` | Подпись пина возвращаемого значения |
| `AdvancedDisplay="Param1,Param2"` | Указанные параметры убираются в расширенные пины |
| `AdvancedDisplay="N"` | Расширенные пины для параметров после первых N |
| `ScriptName="..."` | Имя для поддерживаемого scripting API |

Эти подписи не являются локализацией игрового сообщения. Не заменять ими `FText` и String Table.

### Скрытие, контекст и доступ

| Ключ | Назначение и ограничение |
|---|---|
| `BlueprintProtected` | Вызов через собственный объект в Blueprint, а не произвольный экземпляр |
| `BlueprintInternalUseOnly` | Внутренний строительный блок специальных узлов, не обычный публичный вызов |
| `HidePin="Param"` | Скрытие указанного входного пина в поддерживаемом узле |
| `InternalUseParam="Param"` | Внутренний скрытый параметр, недоступный для обычного подключения |
| `HideSelfPin` | Скрытие Self-пина; не изменение владельца метода |
| `DefaultToSelf="Param"` | Неподключённый подходящий UObject-параметр получает self-контекст |
| `WorldContext="Param"` | Параметр, через который определяется мир |
| `CallableWithoutWorldContext` | Допуск поддерживаемого вызова без обычного обязательного world-контекста |
| `HidePinAssetPicker="Param"` | Скрытие asset picker на соответствующем пине |
| `DataTablePin="Param"` | Связь с DataTable-параметром для поддерживаемого выбора имени строки |

`BlueprintProtected` не имеет обычного полезного смысла для static-метода Blueprint Function Library; UHT проверяет соответствующий конфликт. `HidePin`/`HideSelfPin` не создают авторизацию и не запрещают все C++-пути вызова.

### Ссылки и динамические типы

| Ключ | Назначение и ограничение |
|---|---|
| `AutoCreateRefTerm="Params"` | Подготовка значения для неподключённого reference-пина |
| `DeterminesOutputType="Param"` | Тип поддерживаемого результата определяется class/object-входом |
| `DynamicOutputParam="Param"` | Указание динамически типизируемого выходного параметра |
| `ArrayParm="Params"` | Специальные wildcard-массивы для поддерживаемого узла |
| `ArrayTypeDependentParams="Param"` | Зависимость типов параметров от array-типизации |
| `SetParam="Params"` | Специальная типизация set-параметров |
| `MapParam`, `MapKeyParam`, `MapValueParam` | Специальная типизация map и его ключей/значений |
| `CustomStructureParam="Params"` | Wildcard-структуры; требуется собственный CustomThunk |
| `BlueprintAutocast` | Поддерживаемое автопреобразование через static pure-функцию библиотеки |
| `CommutativeAssociativeBinaryOperator` | Специальный узел ассоциативной/коммутативной операции |
| `IgnoreTypePromotion` | Исключение из поддерживаемого механизма продвижения типов |

**Wildcard** — пин, тип которого выбирается при построении/компиляции графа. Ключ метаданных не делает любую C++-функцию универсальным шаблоном: нужна совместимая сигнатура и обработка реального типа.

Не путать проверенное написание `ArrayParm` с предполагаемым `ArrayParam`. Для динамического результата также нельзя вернуть объект неправильного runtime-класса и надеяться, что подпись пина исправит объект.

### Поток выполнения, latent и расширения

| Ключ | Назначение и ограничение |
|---|---|
| `ExpandEnumAsExecs="Param"` | Exec-ветви по поддерживаемому enum-параметру |
| `ExpandBoolAsExecs="Param"` | Аналогичная схема для bool |
| `Latent` | Поддерживаемый latent-узел с отложенным продолжением |
| `LatentInfo="Param"` | Параметр `FLatentActionInfo`, связывающий продолжение |
| `ForceAsFunction` | Представление поддерживаемого Blueprint-event как функции |
| `NativeMakeFunc` | Специальное представление нативной Make-функции структуры |
| `NativeBreakFunc` | Специальное представление нативной Break-функции структуры |
| `MaterialParameterCollectionFunction` | Специальный узел работы с material parameter collection |

`HasNativeMake`/`HasNativeBreak` относятся к **USTRUCT** и указывают на подходящие функции. Это не то же самое, что `NativeMakeFunc`/`NativeBreakFunc` на самой UFUNCTION.

### Устаревание, редактор и потоки

| Ключ | Назначение и ограничение |
|---|---|
| `DeprecatedFunction` | Предупреждение о Blueprint-вызове устаревшего API |
| `DeprecationMessage="..."` | Пояснение/замена для устаревшего API |
| `DevelopmentOnly` | Дополнительное управление включением Blueprint-вызова для development-сценариев |
| `UnsafeDuringActorConstruction` | Запрет/ограничение вызова в поддерживаемом Construction Script |
| `NotBlueprintThreadSafe` | Исключение из thread-safe декларации подходящей Blueprint Function Library |

`DevelopmentOnly` не удаляет автоматически тело обычного C++-метода и не является надёжным способом спрятать чувствительные операции. `UnsafeDuringActorConstruction` не перехватывает любой прямой нативный вызов.

`BlueprintThreadSafe` в документированном сценарии относится к **классу Blueprint Function Library**; это обещание разработчика инструментам, а не автоматически добавленная синхронизация. `NotBlueprintThreadSafe` задаёт исключение функции. Ни BlueprintPure, ни const сами по себе не делают обращения к UObject безопасными из другого потока.

## 9. Практические примеры meta

### AdvancedDisplay и значения по умолчанию

```cpp
/** Показывает локальное UI-сообщение; длительность можно оставить по умолчанию. */
UFUNCTION(BlueprintCallable, Category = "UI|Notification",
          meta = (DisplayName = "Show Message", AdvancedDisplay = "Duration"))
void ShowMessageAdvanced(const FText& Text, float Duration = 2.0f);
```

Длительность остаётся параметром, но её пин можно свернуть. C++-default не превращает значение в настраиваемое поле WBP: для настройки гейм-дизайнером нужен соответствующий UPROPERTY/конфигурационный объект.

### WorldContext и Latent

В подходящей Blueprint Function Library:

```cpp
/** Объявление локального latent-узла; реальную обработку ожидания нужно реализовать отдельно. */
UFUNCTION(BlueprintCallable, Category = "Utilities",
          meta = (WorldContext = "WorldContextObject",
                  Latent, LatentInfo = "LatentInfo"))
static void WaitForMessage(const UObject* WorldContextObject,
                           float Duration,
                           FLatentActionInfo LatentInfo);
```

`WorldContext` помогает найти мир через переданный объект; не создаёт UWorld. Проверка корректности контекста остаётся в реализации.

**Latent** — вызов с отложенным продолжением Blueprint-потока, например ожидание. Это не отдельный поток ОС и не автоматическая асинхронность. Объявление Latent само не создаёт таймер или действие: нужна реализация, поддерживающая возобновление через latent action infrastructure.

Latent-вызовы имеют ограничения контекста графа и не являются обычным синхронным вызовом с return. Для простого скрытия плашки по таймеру создавать собственную latent-функцию обычно не требуется.

### Enum как Exec-результат

```cpp
UENUM(BlueprintType)
enum class ENotificationResult : uint8
{
    Shown,
    Ignored
};
```

В классе виджета:

```cpp
/** Локально пытается показать сообщение и сообщает выбранный результат. */
UFUNCTION(BlueprintCallable, Category = "UI|Notification",
          meta = (ExpandEnumAsExecs = "Result"))
void TryShowMessage(const FText& Text, ENotificationResult& Result);
```

Неконстантный выходной enum превращается в Exec-ветви результата для поддерживаемого Blueprint-узла. Реализация обязана установить Result на каждом пути: meta не выбирает результат за неё.

### Getter/Setter, связанные с UPROPERTY

```cpp
UPROPERTY(EditDefaultsOnly, BlueprintGetter = GetDisplayDuration,
          BlueprintSetter = SetDisplayDuration, Category = "Notification")
float DisplayDuration = 2.0f;

/** Читает настроенную длительность локального UI. */
UFUNCTION(BlueprintGetter)
float GetDisplayDuration() const;

/** Устанавливает длительность локального UI с необходимыми runtime-проверками. */
UFUNCTION(BlueprintSetter)
void SetDisplayDuration(float NewDuration);
```

UPROPERTY указывает имена аксессоров, а UFUNCTION описывает сами функции. Getter должен быть pure, без входных параметров и с результатом типа поля; setter — callable, не pure, с одним подходящим входом и без return/выходных параметров.

Настройка getter/setter для Blueprint не превращает всякое `DisplayDuration = Value` в C++ или изменение Details в автоматический вызов этого setter. Инварианты и доступность прямого изменения нужно проектировать отдельно.

## 10. UI, динамические делегаты и необходимость макроса

### Публичная операция HUD

Удобно предоставить основному HUD специализированный метод «показать уведомление». Внутри он проверяет дочерний виджет и вызывает его логику. Не обязательно выдавать наружу указатель на виджет ради одного действия.

Если метод вызывается только из C++, UFUNCTION может быть не нужен. Если его должен вызывать Blueprint — подходит BlueprintCallable. Сетевая доставка должна приходить через подходящий объект с ownership, а не через RPC на самом экранном виджете.

### Динамический делегат

Для привязки через динамический механизм, например `AddDynamic`, callback должен быть отражаемым и иметь совместимую сигнатуру:

```cpp
/** Обрабатывает локальное закрытие сообщения; вызывается динамическим делегатом. */
UFUNCTION()
void HandleMessageClosed();
```

BlueprintCallable для такой привязки не обязателен: нужен отражаемый метод, а не обязательно публичный Blueprint-узел.

Обычные нативные делегаты с подходящим `AddUObject`/лямбдой не требуют UFUNCTION только ради самой привязки. Выбирать механизм по задаче, а не добавлять отражение всем методам.

Периоды подписки и отписки должны соответствовать друг другу. UFUNCTION не освобождает от необходимости не дублировать подписки и правильно учитывать жизнь виджета.

### CallInEditor и Exec

```cpp
/** Перестраивает редакторский UI-предпросмотр; не является сетевой игровой командой. */
UFUNCTION(CallInEditor, Category = "Preview")
void RefreshPreview();

/** Диагностическая консольная операция в поддерживаемом Exec-владельце. */
UFUNCTION(Exec)
void PrintNotificationState();
```

Для стандартной кнопки CallInEditor обычно нужна подходящая функция без параметров и результата; доступность кнопки зависит от владельца и редакторского контекста. Это не кнопка игрового UI и не автоматический runtime-вызов.

Exec работает через поддерживаемую цепочку консольных команд, например соответствующий PlayerController. На любом произвольном UObject функция не станет автоматически доступной из консоли.

Не ставить CallInEditor/Exec на удаление данных, публикацию или другие опасные действия как безобидную «подсказку»: это дополнительные пути запуска реального кода.

## 11. Типичные несовместимости и проверка

В проверенном UHT:

- BlueprintImplementableEvent и BlueprintNativeEvent нельзя объединять.
- Blueprint-event не совмещается с RPC или Blueprint-property-accessor.
- Обычный RPC не может быть static и не должен иметь синхронный return.
- Reliable и Unreliable взаимоисключающие; без RPC они недопустимы.
- Pure без выходов отвергается.
- SealedEvent не подходит Blueprint-event.
- Неверная сигнатура getter/setter или FieldNotify отвергается.

Частые логические ошибки, даже если код собирается:

- Вызывать `_Implementation` вместо исходного имени и обходить Blueprint/RPC.
- Считать BlueprintAuthorityOnly сетевой отправкой или авторизацией C++.
- Менять игровое состояние в pure-узле.
- Полагаться на Hidden/Disabled Blueprint-пин как на проверку клиентского запроса.
- Ожидать, что Latent или WorldContext создадут поведение без реализации.
- Делать Expected Gameplay Failure причиной `_Validate = false`.
- Отправлять лишние Reliable RPC из часто вызываемого UI.
- Путать отображаемое имя пина с C++-именем внутри meta.
- Пропускать проверку указателя/контекста при вызове.

Проверять отдельно: ошибки UHT и сборки → вид и сигнатуру Blueprint-узла → переопределения и Parent-вызов → runtime-параметры → standalone/listen/dedicated для сетевого кода.

Изменения отражаемых сигнатур лучше проверять обычной сборкой с перезапуском редактора, а не считать Live Coding доказательством корректного изменения структуры API.

## Вывод

UFUNCTION задаёт контракт метода с Unreal. Callable — вызов из Blueprint; Pure — вычисление данных; Blueprint-event — возможность реализации/переопределения; RPC — сетевой маршрут с требованиями к владению.

Нужно выбирать минимальный набор, который действительно нужен API. Для обычного локального UI часто достаточно обычного C++-метода либо BlueprintCallable; события, RPC, latent и CustomThunk добавляют только при конкретной необходимости.
