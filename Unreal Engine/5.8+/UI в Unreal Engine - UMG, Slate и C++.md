# UI в Unreal Engine: UMG, Slate и C++

UI (User Interface) — пользовательский интерфейс: кнопки, окна, текст, полосы здоровья и другие элементы взаимодействия с игрой. В Unreal Engine его можно создавать как с визуальным редактором, так и полностью на C++.

**Основная мысль:** C++ и визуальная компоновка не исключают друг друга. Для обычного игрового интерфейса удобно собирать внешний вид в UMG Designer, а поведение описывать в C++. Полностью программный интерфейс тоже возможен, но требует больше ручной работы с компоновкой и оформлением.

## 1. UMG, Widget Blueprint и Slate: что есть что

**Виджет** — отдельный элемент интерфейса или составной блок: кнопка, строка предмета, окно инвентаря.

**UMG (Unreal Motion Graphics)** — система создания интерфейса Unreal Engine. Она предоставляет классы виджетов, визуальный редактор и интеграцию с объектной системой движка.

**Widget Blueprint** — ассет пользовательского виджета. Его Designer позволяет собрать дерево элементов и настроить внешний вид, а граф — описать поведение. Использовать граф для игровой логики необязательно: она может находиться в родительском C++-классе.

**Slate** — C++-фреймворк интерфейса, на котором основана значительная часть UMG. Он используется и для инструментов редактора, и для игрового UI; это не технология исключительно для редактора.

| Подход | Компоновка | Поведение | Основной компромисс |
|---|---|---|---|
| UMG Designer + C++ | В Widget Blueprint | В C++ с возможностью расширения в Blueprint | Быстро менять внешний вид, но остаётся ассет разметки |
| UMG полностью на C++ | Программное дерево UMG-виджетов | В C++ | Нет необходимости в Widget Blueprint, но компоновку приходится описывать кодом |
| Slate | Дерево Slate-виджетов на C++ | В C++ | Больше низкоуровневого контроля, но нужно изучить отдельную модель UI |

**Полностью на C++ не означает автоматически быстрее.** Сам выбор языка не доказывает преимущество по времени кадра: важны структура интерфейса и выполняемая работа.

## 2. Практичный старт: UMG Designer + C++

Рассмотрим окно с кнопкой и текстом.

1. Создать C++-класс на основе `UUserWidget`. Он описывает поведение окна.
2. Создать Widget Blueprint с этим классом в качестве родителя.
3. В Designer добавить кнопку и текст, настроить их расположение, размеры и оформление.
4. Объявить в C++ отражаемые свойства нужных типов с метаданными `BindWidget`.
5. Сопоставить имена свойств с именами элементов в Designer. Типы должны быть совместимы.
6. После инициализации связать нажатие кнопки с обработчиком и передать виджету данные для отображения.
7. Создать экземпляр нужного Widget Blueprint через `CreateWidget` с корректным контекстом владеющего игрока и добавить его на экран через `AddToViewport` либо `AddToPlayerScreen`.

Важно создавать именно класс Widget Blueprint, если дерево и оформление находятся в нём. Экземпляр только нативного родительского класса не получает разметку дочернего ассета.

### Что делает BindWidget

`BindWidget` связывает свойство C++-класса с существующим элементом дерева Widget Blueprint. Он **не создаёт кнопку или текст сам**.

Для обязательной привязки компилятор Widget Blueprint проверяет наличие элемента и совместимость типа. `BindWidgetOptional` позволяет отсутствие элемента, поэтому код должен корректно обрабатывать пустую ссылку.

В C++-конструкторе ещё нельзя рассчитывать на готовые привязки: дерево конкретного экземпляра формируется позднее.

### Когда нужен AddToPlayerScreen

`AddToPlayerScreen` добавляет виджет в область экрана конкретного локального игрока, что важно, например, при split-screen. `AddToViewport` добавляет виджет в общий viewport. Выбирать нужно по способу отображения, а не считать эти вызовы полностью взаимозаменяемыми.

## 3. Можно ли обойтись без Widget Blueprint

Да. В C++ можно создать `UUserWidget`, программно собрать его дерево через `WidgetTree`, создать элементы через `ConstructWidget`, назначить `RootWidget` и добавить дочерние элементы в панели.

**Дерево виджетов** — иерархия содержимого окна: например, корневая панель содержит текст и кнопку. **Слот** описывает, как родительская панель размещает конкретного ребёнка: отступы, выравнивание и другие параметры зависят от типа панели.

Следовательно, недостаточно просто создать объект кнопки: его нужно включить в дерево и настроить размещение.

Этот вариант полезен, когда требуется программная компоновка без ассета разметки. Но динамические списки и окна можно делать и гибридно: например, создавать строки в C++, оставляя их оформление в Widget Blueprint. Динамичность сама по себе не требует отказа от Designer.

При программной сборке отдельно продумать момент создания дерева и повторное построение Slate-представления. Нельзя считать, что любой метод жизненного цикла вызывается ровно один раз или что дерево уже готово на каждом этапе.

## 4. Когда выбирать Slate

Slate подходит, если нужен собственный низкоуровневый элемент, особая компоновка или инструмент редактора. Он также пригоден для игрового UI, если преимущества оправдывают усложнение разработки.

Один из базовых классов для составного Slate-виджета — `SCompoundWidget`; его содержимое задаётся через `ChildSlot`.

Не нужно переносить на Slate все привычки работы с UMG:

- UMG-виджеты относятся к `UObject` и участвуют в системе сборки мусора движка.
- Slate-виджеты — не `UObject`; в их модели владения используются `TSharedRef`, `TSharedPtr` и слабые ссылки.
- Для собственного Slate-элемента можно сделать UMG-обёртку на основе `UWidget`, если он должен использоваться в Designer.

Для первого игрового окна обычно проще начать с UMG, а не изучать одновременно все уровни UI.

## 5. Жизненный цикл UUserWidget

У `UUserWidget` есть UObject-экземпляр и связанное с ним Slate-представление. Их жизненные циклы не тождественны.

| Этап | Для чего использовать | На что обратить внимание |
|---|---|---|
| C++-конструктор | Начальные значения объекта | Не рассчитывать на готовые `BindWidget`-поля и игровой мир |
| `NativeOnInitialized` | Однократная настройка игрового экземпляра, например обработчики постоянных элементов | Для обычного Widget Blueprint дерево уже инициализировано; в полностью нативном виджете содержимое зависит от выбранного способа сборки |
| `NativePreConstruct` | Настройка отображения и предпросмотра | Может выполняться в редакторе; учитывать `IsDesignTime()` и отсутствие игровой сессии |
| `NativeConstruct` | Подключение поведения при построении представления | Может вызываться повторно; не дублировать подписки |
| `NativeDestruct` | Освобождение соответствующих подписок и ресурсов представления | Не равен C++-деструктору или окончательному уничтожению UObject |

`NativeOnInitialized` не является безусловным событием для любого объекта: в проверенной реализации `Initialize` учитывает режим дизайнера и наличие контекста игрока; для Blueprint-класса есть дополнительное разрешение вызова без него.

В переопределениях необходимо учитывать реализацию родителя и вызывать соответствующий `Super`: базовые методы выполняют работу движка и вызывают Blueprint-события.

**Правило для подписок:** этап подключения и этап отключения должны соответствовать друг другу. Если подписаться только один раз в `NativeOnInitialized`, а затем отписаться в `NativeDestruct`, повторное появление того же экземпляра само по себе не повторит однократную инициализацию.

## 6. Как связывать UI с игровыми данными

Виджет показывает состояние и сообщает о намерении пользователя. Он не должен становиться единственным владельцем правил боя, инвентаря или стоимости покупки.

Пример обновления полосы здоровья:

1. Игровая система изменяет здоровье.
2. Доступный клиенту источник данных сообщает об изменении.
3. UI получает текущее и максимальное здоровье.
4. Виджет обновляет полосу и текст.

При первом открытии нужно также прочитать актуальное состояние: подписка только на будущие события не заполнит окно, если данные уже изменились раньше.

Для таких обновлений обычно удобно использовать события и делегаты, а не без необходимости опрашивать состояние каждый кадр. Подписки нужно снимать при завершении соответствующего периода использования и восстанавливать при повторном подключении. Если меняется персонаж или другой источник данных, виджет необходимо переподключить.

Пример команды в обратную сторону: кнопка сообщает «хочу купить предмет», а игровая система проверяет возможность покупки. Конкретный способ связи выбирать по задаче: отдельный интерфейс или дополнительный архитектурный слой не обязателен для каждой кнопки.

## 7. Что учитывать в мультиплеере

Экранный UI создаётся локально для нужного игрока. Само дерево UMG-виджетов не является механизмом репликации игрового состояния.

Типичный путь игрового действия:

**Кнопка клиента → объект с корректным сетевым владением, например PlayerController → серверная проверка → изменение состояния → доставка результата клиенту → обновление UI.**

Виджет не становится сетевым Actor только потому, что написан на C++. Серверный RPC для изменения игрового состояния следует размещать на подходящем реплицируемом объекте с корректным владением, а не рассчитывать на прямой сетевой вызов из `UUserWidget`.

Сервер проверяет цену, наличие предмета и допустимость действия независимо от состояния кнопки. Отключённая кнопка — удобство интерфейса, а не защита от некорректного запроса.

Открытие локальной вкладки или изменение громкости не обязаны проходить через сервер. Сетевой обмен нужен там, где затрагивается авторитетное игровое состояние.

На dedicated server нет локального игрового экрана; создавать для него экранный UI не требуется.

## 8. Практика: плашка с текстом в UMG

Разберём обычное короткое уведомление: прямоугольный фон и текст по центру. Внешний вид собираем в Designer, а показ и скрытие описываем в C++. Это учебный пример, а не требование к конкретной игре.

### Иерархия и слоты: почему текст лучше вложить в фон

Удобная структура:

```text
Canvas Panel
└─ Border
   └─ TextBlock
```

`Canvas Panel` размещает плашку в своей области, `Border` рисует фон и задаёт отступы, `TextBlock` отображает текст. `Border` содержит одного непосредственного ребёнка; для нескольких элементов внутрь него можно поставить панель, например `VerticalBox`.

Если `Border` и `TextBlock` сделать соседями в Canvas, их положение и размеры придётся согласовывать отдельно. При вложении фон может подстраиваться под размер текста, а текст размещается относительно фона.

**Слот принадлежит связи «родитель → ребёнок».** У `Border` в этом примере есть `Canvas Panel Slot`, а у текста — `Border Slot`. Поэтому поля в Details отличаются: якоря ищем у плашки в Canvas, выравнивание содержимого — у текста внутри Border.

### Три разных значения «по центру»

| Настройка | Что она центрирует |
|---|---|
| Canvas Slot → Anchors и Alignment | Саму плашку относительно Canvas |
| Border Slot → Horizontal/Vertical Alignment | Текстовый виджет внутри плашки |
| TextBlock → Justification | Строки текста внутри области самого TextBlock |

`Justification = Center` не переносит виджет в центр экрана. Если TextBlock ровно по ширине одной строки, разница между Left и Center может быть незаметна: свободного пространства для смещения почти нет.

Для центрирования плашки в Canvas:

1. У `Border` выбрать Canvas Slot → Anchors: центральную точку, то есть Minimum и Maximum `(0.5, 0.5)`.
2. Установить Alignment `(0.5, 0.5)` и Position `(0, 0)`.
3. У текста в Border Slot выбрать Horizontal Alignment и Vertical Alignment → Center.
4. У TextBlock выбрать Justification → Center, если нужны центрированные строки.

**Anchors** задают опорную точку или область относительно размеров родительского Canvas. **Alignment** задаёт, какая точка самого ребёнка совмещается с этой позицией. С Alignment `(0, 0)` в центре Canvas окажется левый верхний угол плашки; с `(0.5, 0.5)` — её центр.

Это центр **Canvas, а не безусловно экрана**. Для экранного центра область Canvas должна занимать нужную область игрока. Если весь пользовательский виджет вставлен в небольшой слот HUD, внутренние якоря не позволят ему выйти в центр полного экрана.

При точечных якорях поля Position и Size описывают смещение и размер. При растянутых якорях часть полей становится отступами от границ якорной области. Не переносить настройки точечного центрирования на растянутую панель без учёта этой разницы.

### Размер плашки: содержимое, отступы и ограничения

**Desired Size** — желаемый размер, который виджет рассчитывает по содержимому и настройкам. Это не гарантия фактически выделенного пространства: окончательное размещение определяет родитель.

Для короткой плашки удобно включить у `Border` в Canvas Slot **Size To Content** (`Auto Size`). При точечных якорях Canvas использует желаемый размер ребёнка вместо вручную заданного Size. Поэтому сохранённые поля ширины и высоты могут не управлять фактическим размером плашки.

Для начала можно выбрать шрифт 24 и Padding у Border: 24 слева/справа, 12 сверху/снизу. Это стартовые значения, а не универсальный стандарт: плашка будет рассчитывать размер из текста и отступов. Padding — пространство между краем фона и содержимым, а не смещение плашки на экране.

**Auto Size сам по себе не ограничивает длинный текст.** Для более длинных сообщений нужно выделить ограниченную ширину, например через `SizeBox` с `Width Override`, и настроить перенос строк. `Auto Wrap Text` использует доступную ширину, а `Wrap Text At` задаёт явный порог переноса. В полностью свободной по ширине компоновке одного Auto Wrap может быть недостаточно.

Проверять нужно обе локализации, перенос строк и поддержку символов выбранным шрифтом: перевод может оказаться длиннее исходного сообщения.

### DPI и размер шрифта

Размеры компоновки UMG не следует воспринимать как неизменное число физических пикселей на любом экране. UI масштабируется согласно настройкам DPI Scaling и размеру viewport; отображение шрифта также связано с настройкой разрешения шрифтов проекта.

Якоря помогают сохранить положение относительно родителя, но не гарантируют читаемость и отсутствие переполнения. Проверять интерфейс следует в составе HUD, например при 1280×720, 1920×1080 и широком соотношении сторон, а не только в одном размере предпросмотра Designer.

### Прозрачность фона и текста — разные настройки

| Настройка | На что влияет |
|---|---|
| Border → Brush Color | Окраска и прозрачность фоновой кисти |
| Border → Content Color and Opacity | Окраска и прозрачность содержимого Border |
| TextBlock → Color and Opacity | Собственный цвет и прозрачность текста |
| Widget → Render Opacity | Общая прозрачность представления виджета, в том числе его содержимого |

Для тёмного полупрозрачного фона с хорошо читаемым текстом можно начать с Brush Color: чёрный, Alpha 0.65; Content Color and Opacity: белый, Alpha 1; цвет текста — по стилю интерфейса, Alpha 1.

Если установить Content Color and Opacity → Alpha 0.4, прозрачным станет содержимое, а не сама фоновая кисть. Если текст был соседним элементом, это могло не влиять на него; после переноса внутрь Border влияние появится.

Итоговый вид зависит также от тинта и ресурса кисти, цветов и прозрачности предков. Значение Alpha 1 в одном поле не гарантирует полностью непрозрачный результат.

### Видимость и прохождение кликов

| Visibility | Видно | Участвует в разметке | Проверка попадания мыши |
|---|---|---|---|
| Visible | Да | Да | Разрешена для виджета и его детей |
| Hidden | Нет | Да | Нет |
| Collapsed | Нет | Нет | Нет |
| Not Hit-Testable (Self & All Children) | Да | Да | Нет для виджета и детей |
| Not Hit-Testable (Self Only) | Да | Да | Нет для самого виджета; дети могут принимать ввод |

В C++ последние два значения называются `HitTestInvisible` и `SelfHitTestInvisible`. Здесь описаны возможности самого состояния; видимость предков и другие условия тоже могут ограничивать отображение и ввод.

Пример: в `VerticalBox` идут строки A, B, C. `Hidden` у B оставляет пустое место между A и C, а `Collapsed` исключает B из разметки. Ни одно из этих состояний не уничтожает объект.

Для неинтерактивной подсказки поверх игры обычно подходит `HitTestInvisible`: плашка видна, но она и её дети не становятся целями проверки попадания мыши. Не применять это состояние ко всему интерактивному HUD: оно отключит попадание мышью и по его кнопкам. Это настройка hit-testing, а не универсальное управление фокусом клавиатуры.

### Один экземпляр, таймер и повторные сообщения

Простой вариант — создать плашку один раз, изначально скрыть, затем показывать её по событиям. Скрытый объект остаётся в памяти. Повторное создание тоже допустимо: выбор зависит от частоты сообщений, сложности виджета и измерений, а не от правила «кэш всегда быстрее».

`FText` — значение локализованного текста, а `UTextBlock` — отображающий его элемент. Для обновления использовать `SetText`; если текст ссылается на String Table, передавать этот `FText` без промежуточного преобразования в обычную строку и обратно.

Нужно заранее выбрать поведение повторов:

- **Игнорирование:** пока `bIsActive` установлен, новый вызов ничего не меняет; исходный таймер не продлевается.
- **Замена:** обновить текст и перезапустить таймер; старый таймер не должен скрыть новое сообщение.

Для игнорирования последовательность такая: проверить активность → проверить параметры и привязки → установить текст и флаг → показать → запустить одноразовый таймер → скрыть и сбросить флаг. Флаг отражает состояние уведомления, а не запрет игровых действий.

Показ можно завершать сразу, без анимации. Если используется плавное исчезновение, отдельно определить момент сброса активности; завершающий обработчик старой анимации не должен скрыть новое сообщение.

При завершении использования виджета нужно очистить его таймер, если доступен мир, сбросить состояние и вызвать родительский `NativeDestruct` независимо от наличия мира. Само скрытие не равно `NativeDestruct` и не означает автоматическую остановку таймеров. Если уведомление сопровождается звуком, игнорируемый повтор не должен воспроизводить звук; ограничение повторов применяется ко всему уведомлению.

**`RemoveFromParent` — удаление из родителя, не мгновенное освобождение памяти.** UObject может продолжать жить из-за удерживающих ссылок; сборка мусора освобождает его, когда он становится недостижимым для GC.

### Быстрая диагностика в Designer

Если плашка выглядит неправильно, проверять в таком порядке: иерархия → тип родительского слота → якоря и Alignment → Auto Size и доступная ширина → Padding → Justification → цвета и Alpha → видимость и ввод.

Скомпилировать Widget Blueprint, проверить имена обязательных `BindWidget`-элементов, затем открыть UI в игре. Отдельно проверить смену языка, длинный текст, повторные вызовы и клики по игровому миру под плашкой. Корректные свойства в Designer ещё не доказывают корректное размещение в реальном HUD.

## 9. Клавиатурный ввод, фокус и режимы ввода

Видимость виджета, hit-testing мыши, режим ввода `PlayerController` и клавиатурный фокус — связанные, но разные вещи. Видимый виджет сам по себе не означает, что он получает клавиши; показ курсора сам по себе не переводит клавиатурный фокус. Навигация с клавиатуры или геймпада опирается на фокус и правила навигации, а не на hit-testing мыши.

### Режим ввода

Режим задаётся через `APlayerController::SetInputMode` на локальном контроллере:

- `FInputModeGameOnly` направляет ввод в игровой viewport и при установке фокусирует viewport.
- `FInputModeUIOnly` оставляет ввод UI и блокирует игровой ввод через viewport. Закрытие такого окна нужно обрабатывать в UI; не рассчитывай на gameplay Input Action или `UUserWidget::ListenForInputAction`.
- `FInputModeGameAndUI` не блокирует игровой ввод в viewport, но это не гарантирует одновременную доставку клавиатурного события в UI и игру. Клавиша маршрутизируется по Slate focus path: если фокус находится на UMG-виджете, `SViewport` не входит в этот путь и PlayerController автоматически не получает эту клавишу. `Unhandled` продолжает UI-маршрут, но само по себе не передаёт событие игре. Мышь маршрутизируется отдельно и может попадать в viewport по hit-test.

`UIOnly` и `GameAndUI` не выбирают нужный интерактивный элемент автоматически: передай в режим явную цель фокуса и проверь, что она поддерживает клавиатурный фокус. `bShowMouseCursor` управляет отображением курсора, но сама по себе не задаёт клавиатурный фокус.

### Фокус и обработка клавиши

Slate focus path — путь от окна через его родителей к сфокусированному виджету. Для получения клавиатурных событий нужен соответствующий путь фокуса. Если фокус назначается самому `UUserWidget`, проверь `IsFocusable`/`SupportsKeyboardFocus`: по умолчанию `UUserWidget` не поддерживает клавиатурный фокус. Целью фокуса может быть и интерактивный дочерний виджет. Родителю не обязательно самому быть focusable, чтобы обрабатывать событие на пути сфокусированного потомка.

`OnPreviewKeyDown` позволяет родителю обработать клавишу до сфокусированного потомка. Если preview-обработчик возвращает `Handled`, потомок не получает эту клавишу в `OnKeyDown`. Иначе `OnKeyDown` начинается на сфокусированном виджете и всплывает к родителям, пока событие не обработано. `Handled` прекращает дальнейшую обработку по текущему маршруту; `Unhandled` позволяет продолжить её по маршруту UI, но не обещает передачу игровому действию. Preview-обработка родителем допустима, когда она нужна; заранее определи, какой слой в итоге должен потребить клавишу.

### При открытии и закрытии UI

При открытии согласованно настрой режим ввода, курсор и фокус на доступный для клавиатуры элемент, при необходимости передав этот элемент как цель фокуса. При закрытии убери или скрой окно и явно восстанови ожидаемые режим ввода и фокус. Для нескольких окон или оверлеев восстанавливай контекст, активный до закрытия, а не безусловно переключай всё в `GameOnly`.

### Короткая диагностика

1. Какой локальный `PlayerController` активен и какой `SetInputMode` был последним?
2. Какой элемент находится в focus path и поддерживает ли он keyboard focus? Передан ли он как цель фокуса в `UIOnly` или `GameAndUI`?
3. Доходит ли клавиша до `OnPreviewKeyDown`/`OnKeyDown`, и какой ответ возвращается?
4. Какая система должна обработать клавишу? При `UIOnly` не рассчитывай на gameplay Input Action для закрытия окна; при `GameAndUI` проверь, находится ли viewport в focus path.
5. Восстанавливает ли закрытие окна предыдущие режим ввода и фокус?
6. Не перепутаны ли видимость и hit-testing мыши с keyboard focus?

## 10. Что читать и в каком порядке

### Первый проход: получить рабочее окно

1. [UMG UI Designer](https://dev.epicgames.com/documentation/en-us/unreal-engine/umg-ui-designer-for-unreal-engine) — основы виджетов, Designer и дерева интерфейса.
2. Справочник Epic по `UUserWidget` — создание экземпляра, владеющий игрок, добавление на экран и события жизненного цикла.
3. Справочники по `UButton`, `UTextBlock` и выбранной панели — один небольшой законченный пример вместо изучения всех элементов сразу.
4. Компоновка UMG: панели, слоты, anchors для Canvas Panel, выравнивание и DPI scaling.
5. Фокус, режим ввода и навигация клавиатурой/геймпадом — чтобы окно было не только видно, но им можно было пользоваться.

### Второй проход: понять реализацию

- [Slate UI Framework](https://dev.epicgames.com/documentation/en-us/unreal-engine/slate-ui-framework-in-unreal-engine) — архитектура Slate и создание собственных элементов.
- Делегаты Unreal Engine — подключение обработчиков и управление временем жизни подписок.
- Репликация и владение объектами — граница между локальным UI и серверными игровыми действиями.

Ссылки на документацию — маршрут дальнейшего чтения, а не подтверждение совпадения всех примеров сайта с установленной версией. Детали жизненного цикла в этой заметке проверены по локальным исходникам движка.

## Вывод

Сделать UI на C++ можно. Начальный выбор — не «C++ или Blueprint вообще», а **где удобнее хранить компоновку и где должно находиться поведение**.

Для обычного игрового окна разумная отправная точка — UMG Designer для внешнего вида и C++ для логики. Полностью нативный UMG и Slate — доступные альтернативы, когда их преимущества действительно нужны.
