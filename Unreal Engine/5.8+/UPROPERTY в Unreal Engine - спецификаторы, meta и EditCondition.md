# UPROPERTY в Unreal Engine: спецификаторы, meta и EditCondition

`UPROPERTY` описывает поле для системы отражения Unreal Engine: редактора, Blueprint, сериализации, сборки мусора и других механизмов. Это не просто команда «показать переменную в Details».

**Основная мысль:** отдельно выбирать, кто редактирует поле, кто читает его в Blueprint, как оно хранится и какие подсказки получает редактор. `meta` оформляет и настраивает работу инструментов, но не заменяет проверки в игровом коде.

Материал рассчитан на UE 5.8 и базовое знание C++. Сначала удобно прочитать разделы 1–5 и 8; разделы 6–7 — справочник для возвращения к отдельным ключам.

## 1. Что происходит при объявлении UPROPERTY

Unreal Header Tool (**UHT**) разбирает отражаемые объявления и генерирует код, с помощью которого движок получает описание поля: имя, тип, флаги и метаданные.

Обычный компилятор C++ не реализует смысл `EditDefaultsOnly`: это часть инфраструктуры Unreal. Поле объявляется внутри отражаемого класса `UCLASS` или структуры `USTRUCT`, использующих `GENERATED_BODY`. Не любой C++-тип поддерживается отражением; например, вместо произвольного стандартного контейнера обычно используют поддерживаемые контейнеры UE.

Пример внутри такого класса:

```cpp
UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = "Notification",
          meta = (ClampMin = "0.1", ClampMax = "10.0",
                  UIMin = "0.5", UIMax = "5.0", Units = "s"))
float DisplayDuration = 2.0f;
```

Разбор:

- `float DisplayDuration = 2.0f` — обычное поле C++ и его начальное значение.
- `EditDefaultsOnly` — редактирование значений по умолчанию, а не индивидуальных экземпляров.
- `BlueprintReadOnly` — Blueprint может читать поле, но не записывать его обычным узлом Set.
- `Category` — группа в инструментах редактора.
- `meta = (...)` — набор ключей с дополнительной информацией.
- `ClampMin`, `ClampMax` — границы редакторского числового поля.
- `UIMin`, `UIMax` — удобный диапазон ползунка.
- `Units = "s"` — единицы измерения для редактора.

Здесь нет автоматического таймера, репликации или запуска уведомления. Макрос описывает поле, а поведение пишется отдельно.

Все фрагменты ниже — отдельные учебные объявления, а не готовый модуль. Для объектных типов нужны соответствующие объявления/инклюды, а для WBP — дочерний ассет и корректные привязки. Примеры проверены чтением первоисточников и по безопасности, но не компилировались как самостоятельный проект.

## 2. Спецификаторы, meta и обычный C++ — три разных слоя

| Слой | Примеры | Что определяет |
|---|---|---|
| Доступ C++ | `public`, `protected`, `private` | Какие участки C++ могут обращаться к члену |
| Спецификаторы UPROPERTY | `EditDefaultsOnly`, `BlueprintReadOnly`, `Transient`, `Replicated` | Участие поля в механизмах Unreal |
| Метаданные | `EditCondition`, `ClampMin`, `BindWidget`, `DisplayName` | Дополнительные инструкции UHT, редактору и другим инструментам |

`UPROPERTY()` без аргументов тоже полезен: поле отражается, а отражаемая объектная ссылка может участвовать в обходе GC. Доступ в Details или Blueprint при этом не появляется автоматически.

Граница не сводится к «спецификаторы всегда runtime, meta всегда косметика». Например, `EditDefaultsOnly` управляет редактором, а `BindWidget` участвует в подготовке привязки, используемой во время игры. Но игровая логика не должна зависеть от чтения редакторских метаданных в packaged build.

### Как записывать meta

Ключи разделяются запятыми; строковые значения заключаются в двойные кавычки:

```text
meta = (ClampMin = "0.1", DisplayName = "Display Duration", EditConditionHides)
```

Некоторые ключи — признаки присутствия (`EditConditionHides`), другие ожидают значение (`EditCondition = "bEnableSound"`). Формат определяется потребителем конкретного ключа: нельзя считать, что все ключи одинаково обрабатывают отсутствие значения или строку `"false"`.

`Category` обычно пишут снаружи `meta`; `DisplayName`, `ToolTip`, условия и ограничения — внутри. Общий парсер допускает и некоторые дополнительные формы записи, но для читаемости лучше придерживаться привычного синтаксиса.

## 3. Где поле видно и кто может его изменять

### Defaults и Instance

**Defaults** — значения по умолчанию класса/шаблона. В Blueprint их обычно настраивают через Class Defaults. **CDO** (Class Default Object) — объект, представляющий значения по умолчанию класса.

**Instance** — конкретный созданный экземпляр. Например, отдельный Actor, размещённый на уровне. Изменение его настроек не означает изменение всех экземпляров класса.

| Спецификатор | Defaults | Instance | Редактирование через Details |
|---|---|---|---|
| `EditAnywhere` | Да | Да | Разрешено |
| `EditDefaultsOnly` | Да | Нет | Только defaults |
| `EditInstanceOnly` | Нет | Да | Только экземпляр |
| `VisibleAnywhere` | Да | Да | Только отображение |
| `VisibleDefaultsOnly` | Да | Нет | Только отображение defaults |
| `VisibleInstanceOnly` | Нет | Да | Только отображение экземпляра |

Это правила для стандартного отображения свойств; конкретный редактор или customization может дополнительно влиять на Details. Выбирают **один** из этих шести спецификаторов: комбинация `EditAnywhere` и `VisibleAnywhere` не имеет смысла и отвергается UHT.

Для настройки длительности в дочернем Widget Blueprint обычно достаточно `EditDefaultsOnly`: гейм-дизайнер меняет Class Defaults, а C++ читает это поле.

### Доступ из Blueprint независим от Details

| Спецификатор | Чтение в графе Blueprint | Запись обычным Set |
|---|---|---|
| `BlueprintReadOnly` | Да | Нет |
| `BlueprintReadWrite` | Да | Да |
| Ни один из них | Не открывается этим объявлением | Не открывается этим объявлением |

Следовательно, `EditDefaultsOnly` не требует `BlueprintReadWrite`. Если значение настраивают в Details, а использует только C++, доступ из графа можно вообще не добавлять.

`VisibleAnywhere, BlueprintReadWrite` означает: через Details поле не редактируется, но граф может его менять. Это не противоречие — речь о разных способах доступа. `BlueprintReadOnly` не запрещает изменения из C++.

У объектной ссылки «нельзя редактировать поле» не всегда означает «нельзя настраивать объект, на который оно ссылается». Например, можно запретить замену ссылки на компонент, сохранив редактирование отдельных настроек компонента.

### Private и AllowPrivateAccess

Открытие приватного поля в Blueprint требует явного разрешения:

```cpp
private:
    UPROPERTY(BlueprintReadOnly, meta = (AllowPrivateAccess = "true"))
    float Progress = 0.0f;
```

Это не превращает поле в `public` для C++. Альтернатива — поместить подходящее поле в `protected` или предоставить отдельный метод доступа.

`AllowPrivateAccess` не нужно добавлять ко всем полям. Оно решает конкретный конфликт между приватностью C++ и намеренным доступом Blueprint.

## 4. Условия редактирования: EditCondition

### Основной пример

```cpp
UPROPERTY(EditDefaultsOnly, Category = "Notification")
bool bEnableSound = true;

UPROPERTY(EditDefaultsOnly, Category = "Notification",
          meta = (EditCondition = "bEnableSound", EditConditionHides))
TObjectPtr<USoundBase> NotificationSound = nullptr;
```

Когда `bEnableSound` выключен:

- с одним `EditCondition` поле звука остаётся видно, но недоступно для редактирования;
- с дополнительным `EditConditionHides` поле скрывается.

Ни один вариант не очищает `NotificationSound` и не запрещает C++ использовать звук. Код воспроизведения отдельно проверяет включение и наличие подходящего ассета.

Условия используют отражаемые имена полей, а не подписи `DisplayName`. Для обычного сценария условие ссылается на поля содержащего объекта/структуры.

### Выражения и ключевые операции

`EditCondition` — строка для отдельного парсера, **не произвольный код C++**. В установленном UE поддерживаются:

| Вид проверки | Пример строки условия |
|---|---|
| Булев флаг | `bEnableSound` |
| Отрицание флага | `!bEnableSound` |
| И / ИЛИ | `bEnableSound && bUseCustomSound`, `bEnableSound || bPreview` |
| Группировка | `bEnableSound && (Volume > 0.0 || bPreview)` |
| Числовое сравнение | `DisplayDuration > 0.0`, `Count >= 1` |
| Равенство / неравенство | `Count == 0`, `Count != 0` |
| Перечисление | `Style == ENotificationStyle::Expanded` |
| Объектный указатель | `NotificationSound != nullptr` |
| Арифметика | `Count > MinimumCount + 1` |
| Побитовое И | `Flags & ENotificationFlags::Sound` |

Кроме показанных сравнений поддерживаются `<`, `<=`, `>`, `>=`, а в арифметике — `+`, `-`, `*`, `/`. `true`, `false`, `nullptr` и `INDEX_NONE` распознаются парсером. Не переносить сюда автоматически весь набор операторов C++.

Для указателя безопаснее пользоваться явным `!= nullptr`, а не предполагать поддержку преобразования указателя в bool. Для чисел использовать обычную запись вроде `0.0`, без C++-суффикса `f`.

Пример с перечислением:

```cpp
UENUM()
enum class ENotificationStyle : uint8
{
    Compact,
    Expanded
};
```

В отражаемом классе:

```cpp
UPROPERTY(EditDefaultsOnly, Category = "Notification")
ENotificationStyle Style = ENotificationStyle::Compact;

UPROPERTY(EditDefaultsOnly, Category = "Notification",
          meta = (EditCondition = "Style == ENotificationStyle::Expanded"))
float ExpandedPadding = 24.0f;
```

Не писать в условии произвольные вызовы `IsValid(...)`, `Array.Num()` или обращения к любой цепочке C++-объектов. Парсер поддерживает отдельные сценарии чтения отражаемых функций, включая проверенные в исходниках функции без параметров, но это не общий механизм исполнения выражений C++. Для сложной панели может понадобиться Details customization вместо длинного условия.

### InlineEditConditionToggle

На булевом управляющем поле можно указать:

```cpp
UPROPERTY(EditDefaultsOnly, Category = "Notification",
          meta = (InlineEditConditionToggle))
bool bEnableSound = true;
```

Это **альтернативное объявление** поля из первого примера, а не второе поле с тем же именем. Если другое свойство использует его в простом `EditCondition`, переключатель можно показывать рядом с этим свойством вместо отдельной строки bool.

`InlineEditConditionToggle` относится к управляющему bool, `EditCondition` — к зависимому полю. Для переключателя рядом с редактируемым полем обычно не требуется `EditConditionHides`: иначе вместе со строкой можно скрыть удобное место переключения. Сложное выражение из нескольких полей не равно простому inline-переключателю.

## 5. Числовые границы, Units и runtime-проверки

Возвращаемся к `DisplayDuration` из первого примера:

- `ClampMin = "0.1"`, `ClampMax = "10.0"` ограничивают ввод через стандартный числовой редактор.
- `UIMin = "0.5"`, `UIMax = "5.0"` задают диапазон ползунка, но не самостоятельный запрет ручного ввода.
- `Units = "s"` объясняет редактору, что значение интерпретируется в секундах; не создаёт таймер и не меняет автоматически единицы игровой математики.

При этих настройках ручной ввод `8.0` допустим, а ползунок удобен для диапазона 0.5–5.0. Если UIMin/UIMax отсутствуют, стандартный числовой редактор может взять границы ползунка из ClampMin/ClampMax.

**Метаданные не перехватывают каждое присваивание.** Значение может прийти из C++, Blueprint, старого ассета, сохранения или другого пути загрузки. В месте использования нужно проверять необходимые инварианты: например, длительность положительна и конечна. Для авторитетных игровых действий клиентские данные дополнительно проверяет сервер.

`EditCondition`, `AllowedClasses` и `NoClear` тоже не являются runtime-валидацией, авторизацией или защитой от некорректного ввода.

## 6. Справочник спецификаторов UPROPERTY

Ниже перечислены все 45 специализированных обработчиков поля из локального `UhtPropertyMemberSpecifiers.cs`, включая устаревшие и экспериментальные, плюс общеупотребимые `Category` и `meta`. Это перечень конкретной версии исходников, не обещание неизменности API будущих версий.

### Редактирование и Blueprint

| Ключ | Назначение и ограничение |
|---|---|
| `EditAnywhere` | Редактирование defaults и экземпляров |
| `EditDefaultsOnly` | Редактирование только defaults |
| `EditInstanceOnly` | Редактирование только экземпляров |
| `VisibleAnywhere` | Отображение defaults и экземпляров без редактирования поля |
| `VisibleDefaultsOnly` | Отображение только defaults |
| `VisibleInstanceOnly` | Отображение только экземпляров |
| `BlueprintReadOnly` | Чтение из Blueprint, без обычного Set |
| `BlueprintReadWrite` | Чтение и запись из Blueprint |
| `BlueprintGetter=FunctionName` | Пользовательский getter для доступа из Blueprint; без write-доступа поле становится Blueprint-read-only |
| `BlueprintSetter=FunctionName` | Пользовательский setter для Blueprint; подразумевает write-доступ |
| `Category="UI\|Notification"` | Категория и вложенная подкатегория |
| `meta=(...)` | Передача ключей метаданных |
| `SimpleDisplay` | Поле показывается без раскрытия Advanced |
| `AdvancedDisplay` | Поле помещается в расширенную часть Details |
| `EditFixedSize` | Для динамического массива: редактор не позволяет менять число элементов; не делает массив неизменяемым в C++ |
| `Interp` | Поле предназначено для управления через поддерживаемые треки Sequencer; также получает edit/Blueprint-visible флаги |

Для `BlueprintGetter` и `BlueprintSetter` нужны подходящие отражаемые функции в том же классе. Getter возвращает тип поля, setter принимает значение этого типа. Эти спецификаторы не поддерживаются как произвольные аксессоры членов USTRUCT.

Не объединять `BlueprintReadOnly` с `BlueprintReadWrite` или `BlueprintSetter`.

### Делегаты

| Ключ | Назначение |
|---|---|
| `BlueprintAssignable` | Подписка/привязка к поддерживаемому multicast-делегату из Blueprint |
| `BlueprintCallable` | В UPROPERTY относится к вызываемому из Blueprint multicast-делегату, а не к обычному полю |
| `BlueprintAuthorityOnly` | Для multicast-делегата: ограничивает Blueprint-привязки событиями, помеченными соответствующим authority-ограничением |

Пример объявления динамического multicast-делегата:

```cpp
DECLARE_DYNAMIC_MULTICAST_DELEGATE(FOnNotificationClosed);
```

Поле внутри класса:

```cpp
UPROPERTY(BlueprintAssignable, Category = "Notification")
FOnNotificationClosed OnNotificationClosed;
```

Это описание события, а не автоматический вызов при закрытии. Его нужно вызвать в соответствующей логике.

Важная тонкость: **`BlueprintCallable` существует и у UPROPERTY, и у UFUNCTION, но смысл зависит от контекста.** Перед обычной функцией нужен `UFUNCTION(BlueprintCallable)`, не `UPROPERTY`.

### Хранение, конфигурация и копирование

| Ключ | Назначение и ограничение |
|---|---|
| `Config` | Поле участвует в конфигурации `.ini` класса, настроенного через `UCLASS(Config=...)`; не означает автоматическое сохранение при любом присваивании |
| `GlobalConfig` | Config-поле с использованием конфигурации объявляющего класса, а не отдельного переопределения по подклассам |
| `Transient` | Поле исключается из обычного сохраняемого состояния; не превращает объектную ссылку в слабую |
| `DuplicateTransient` | При дублировании сбрасывает значение к default, а не обязательно к нулю |
| `NonPIEDuplicateTransient` | Аналогичный сброс, кроме дублирования для Play In Editor |
| `TextExportTransient` | Поле не включается в текстовый экспорт, используемый, например, копированием |
| `SkipSerialization` | Исключение из обычной сериализации свойства; текстовый экспорт может оставаться доступным |
| `SaveGame` | Пометка для сериализатора сохранений, который учитывает этот флаг |
| `NonTransactional` | Изменения свойства не включаются в обычную редакторскую историю Undo/Redo |
| `AssetRegistrySearchable` | Значение подходящего поля ассета публикуется для поиска в Asset Registry; не для произвольного struct-поля или параметра |

`Config` обычно требует явной операции вроде `SaveConfig`, когда нужно сохранить изменения. Не использовать его как синоним `EditDefaultsOnly`.

`SaveGame` не сохраняет объект на диск само по себе и не означает, что любые поля без этого флага никогда не сериализуются. Конкретная система/архив определяет правила чтения и записи.

### Объектные ссылки и вложенные объекты

| Ключ | Назначение и ограничение |
|---|---|
| `Instanced` | Для подходящих UObject-ссылок: поддержка индивидуального вложенного экземпляра вместо обычной общей ссылки; включает связанные export/instancing флаги |
| `Export` | При поддерживаемом копировании объект экспортируется как вложенный объект, а не только как ссылка |
| `NoClear` | Скрывает редакторскую возможность очистить объектную ссылку; не гарантирует ненулевой указатель во время игры |

`Instanced` не предназначен для превращения любого общего ассета в независимую копию. Сценарий должен соответствовать вложенным UObject и их классу; для редактируемых inline-объектов обычно нужна подходящая настройка класса, например `EditInlineNew`. Это уже спецификатор UCLASS.

### Репликация

| Ключ | Назначение и ограничение |
|---|---|
| `Replicated` | Пометка поля для репликации |
| `ReplicatedUsing=FunctionName` | Репликация с RepNotify-функцией |
| `NotReplicated` | Исключение члена структуры из поддерживаемой репликации структуры; не общий способ помечать локальное поле любого класса |

Для поля Actor:

```cpp
UPROPERTY(ReplicatedUsing = OnRep_Health)
float Health = 100.0f;
```

Это **не завершённая реализация**: нужны отражаемая `OnRep_Health`, настройка репликации объекта и регистрация свойства в `GetLifetimeReplicatedProps` либо соответствующем используемом механизме. Авторитетные изменения выполняет сервер.

Член структуры нельзя сделать самостоятельным сетевым объектом, просто поставив на него `Replicated`: UHT отвергает такое применение. Локальный UI обычно вообще не требует репликации своих полей; данные и уведомления доставляются через подходящие игровые объекты.

### Более специальные механизмы UE 5.8

| Ключ | Назначение и ограничение |
|---|---|
| `Getter`, `Getter=Name`, `Getter=Auto`, `Getter=None` | Настройка нативного аксессора отражаемого свойства; только для членов класса |
| `Setter`, `Setter=Name`, `Setter=Auto`, `Setter=None` | Настройка нативного mutator; не синоним BlueprintSetter |
| `FieldNotify` | Участие в системе уведомлений изменения поля, используемой в том числе MVVM; требует подходящего класса/инфраструктуры |
| `ForcePostConstructLink` | Внутренний флаг включения свойства в post-construction обработку; не обычная игровая настройка |
| `ExperimentalOverridableLogic` | Экспериментальная инфраструктура переопределяемых свойств |
| `ExperimentalAlwaysOverriden` | Специальный экспериментальный режим override; написание `Overriden` взято из исходников |
| `ExperimentalNeverOverriden` | Специальный экспериментальный режим запрета override |
| `ExperimentalExternalObjects` | Экспериментальная обработка внешних объектов; требует `ExperimentalOverridableLogic` |

Нативные Getter/Setter не делают обычное C++-присваивание `Field = Value` автоматическим вызовом setter. `FieldNotify` тоже не означает, что любое прямое изменение поля само оповестит UI: нужно использовать предусмотренный механизм уведомления.

Экспериментальные и внутренние ключи перечислены для полноты, а не как рекомендация для первой реализации UI.

### Устаревшие и вводящие в заблуждение записи

| Запись | Статус в проверенном локальном UHT |
|---|---|
| `Localized` | Устарел, выдаётся ошибка; для пользовательского текста применять `FText` и механизм локализации |
| `EditInline` | Устарел, ошибка; для подходящего сценария рассмотреть `Instanced` |
| `RepRetry` | Устарел, ошибка |
| `NonPIETransient` | Устаревший alias с предупреждением; использовать `NonPIEDuplicateTransient` |

В веб-таблицах и старых статьях также встречаются `Native`, `NoExport`, `SerializeText` как property-теги. В проверенном файле специализированных обработчиков UE 5.8 их нет: не копировать такие объявления без проверки используемого UHT. Одноимённый ключ у другого макроса не делает его допустимым у UPROPERTY.

Общий `UhtDefaultSpecifiers.cs` содержит ещё общие обработчики, например `DisplayName` и `FriendlyName`, а также ключи, предназначенные прежде всего для классов и других объявлений. Наличие общего обработчика не доказывает полезный смысл ключа для поля. `Blueprintable`, `BlueprintType`, `CallInEditor` и подобные записи не заменяют свойства доступа поля из таблиц выше.

## 7. Справочник meta: ключи, значения и область применения

**Единого закрытого списка всех meta нет.** Общий парсер UHT принимает пары ключ–значение, а смысл ключа задают UHT, редактор, Blueprint-компилятор, конкретный тип или плагин. Неизвестный ключ может сохраниться, но ничего не сделать.

Поэтому «скомпилировалось» не равно «метаданные работают». Указанный ниже набор объединяет property-метаданные из документации Epic и часто используемые ключи из исходников. Это не список метаданных UFUNCTION/UCLASS, которые нельзя бездумно переносить сюда.

### Оформление и порядок

| Ключ | Значение |
|---|---|
| `DisplayName="..."` | Подпись в редакторе; имя C++ остаётся прежним |
| `ToolTip="..."` | Подсказка; не локализованный игровой текст |
| `DisplayAfter="Field"` | Размещение после другого поля, обычно в той же категории |
| `DisplayPriority="N"` | Приоритет сортировки; меньшие значения имеют более высокий приоритет |
| `DisplayThumbnail="true"` | Показ миниатюры подходящего ассета |
| `NoResetToDefault` | Скрытие стандартного Reset to Default там, где редактор поддерживает ключ |
| `ShowOnlyInnerProperties` | Для подходящей структуры: показать внутренние свойства без обычной внешней строки |
| `TitleProperty="Field"` | Подпись элементов массива структур из выбранного поля |
| `ScriptName="..."` | Имя в поддерживаемом экспортируемом scripting API |

### Строки, пути и массивы

| Ключ | Значение и контекст |
|---|---|
| `MultiLine="true"` | Многострочный редактор поддерживаемой строки/текста |
| `PasswordField="true"` | Маскирование вводимых символов; не шифрование и не безопасное хранилище |
| `GetOptions="FunctionName"` | Источник вариантов для поддерживаемого поля, например FName/FString; формат функции зависит от реализации редактора |
| `ContentDir` | Выбор папки Content для подходящего `FDirectoryPath` |
| `LongPackageName` | Представление пути как длинного имени пакета для поддерживаемого path customization |
| `FilePathFilter="..."` | Фильтр файлов в редакторе `FFilePath` |
| `EditFixedOrder` | Запрет перетаскивания элементов массива для изменения порядка |

Не путать `EditFixedSize` с `EditFixedOrder`: первое — спецификатор UPROPERTY для размера массива, второе — meta для порядка элементов.

### Blueprint, UMG и специальные данные

| Ключ | Значение и контекст |
|---|---|
| `AllowPrivateAccess="true"` | Намеренный Blueprint-доступ к приватному полю C++ |
| `ExposeOnSpawn="true"` | Вход значения при создании через поддерживаемый Blueprint-узел; обычно требуется Blueprint-visible поле |
| `BindWidget` | Обязательная привязка поля к элементу Widget Blueprint |
| `BindWidgetOptional` | Необязательная привязка; отсутствие элемента нужно обработать |
| `BindWidgetAnim` | Привязка к анимации Widget Blueprint; поле анимации должно быть `Transient` |
| `BindWidgetAnimOptional` | Необязательная привязка анимации |
| `BlueprintCompilerGeneratedDefaults` | Особое обращение с defaults, созданными Blueprint-компилятором, при копировании между обновлёнными объектами |
| `ConfigHierarchyEditable` | Дополнительная настройка редактирования config-поля в конфигурационной иерархии |

**Sparse Class Data** — отдельная инфраструктура хранения данных класса, не обычные поля каждого экземпляра. `GetByRef` не следует добавлять к любому большому struct в надежде избежать копирования.

## 8. UPROPERTY и UI: готовые формы объявления

### Настраиваемый текст

```cpp
UPROPERTY(EditDefaultsOnly, Category = "Notification")
FText Message;
```

В Class Defaults можно выбрать ссылку на запись String Table. `FText` подходит для локализованного текста. `DisplayName`/`ToolTip` оформляют редактор и не заменяют локализацию самого сообщения.

### Привязка TextBlock

```cpp
protected:
    UPROPERTY(BlueprintReadOnly, meta = (BindWidget))
    TObjectPtr<UTextBlock> MessageText = nullptr;
```

В дочернем Widget Blueprint нужен совместимый элемент с именем `MessageText`. Метаданные не создают TextBlock — связывают поле с существующим деревом. Для обычного вызова `SetText` из C++ доступ BlueprintReadOnly сам по себе не обязателен.

### Привязка анимации

```cpp
protected:
    UPROPERTY(Transient, meta = (BindWidgetAnim))
    TObjectPtr<UWidgetAnimation> FadeOut = nullptr;
```

Нужна анимация `FadeOut` в Widget Blueprint. `Transient` относится к правилам хранения поля, а `BindWidgetAnim` — к привязке; это разные задачи.

Не открывать связанный TextBlock или анимацию как `EditAnywhere` только ради доступа из C++: привязка должна оставаться под управлением WBP, а не ручного назначения ссылки.

## 9. UPROPERTY, ссылки и сборка мусора

Сильная отражаемая ссылка у достижимого для GC владельца помогает удерживать объект:

```cpp
UPROPERTY(Transient)
TObjectPtr<UObject> CachedObject = nullptr;
```

**GC** (Garbage Collection) — сборщик мусора. Он обходит известные ему ссылки и определяет, какие объекты остаются достижимыми. Если сам владелец стал недостижимым, его поле не удерживает всю цепочку навсегда.

`Transient` не означает «GC может немедленно удалить объект»; он про сериализацию, а не слабость ссылки. Для слабого наблюдения существуют `TWeakObjectPtr`, для ссылок на ассеты без постоянного удержания загруженного UObject — `TSoftObjectPtr` со своей моделью загрузки.

`TObjectPtr` без отражаемого поля или другого механизма регистрации ссылок не стоит считать самостоятельной заменой участия владельца в GC. В обычном UObject-классе ссылку, которую должен видеть GC, объявляют через UPROPERTY.

Для обычного булева состояния, читаемого только C++, UPROPERTY не обязателен. Он нужен, если поле должно участвовать в отражении или связанных механизмах.

## 10. Как выбрать и проверить объявление

Короткий порядок:

1. Определить, нужно ли отражение вообще.
2. Выбрать место настройки: defaults, экземпляр или только C++.
3. Независимо решить, нужен ли доступ Blueprint и какой.
4. Определить правила хранения: обычное поле, transient, config, save system.
5. Проверить владение объектными ссылками и необходимость репликации.
6. Добавить только полезные meta: подпись, условия, границы, привязки.
7. Проверить UHT, Details и поведение в runtime по отдельности.

Типовые ошибки:

- `UPROPERTY(BlueprintCallable)` перед обычной функцией.
- Два edit/visibility-спецификатора одновременно.
- `BlueprintReadOnly` и `BlueprintReadWrite` одновременно.
- Ожидание, что `EditDefaultsOnly` автоматически открывает поле в графе.
- Опечатка в имени поля внутри EditCondition или BindWidget.
- Ожидание автоматического игрового запрета из EditCondition.
- Ожидание, что ClampMin остановит прямое присваивание из C++.
- Использование meta от другого макроса или типа без поддерживающего потребителя.
- Ожидание автоматической репликации от одного слова Replicated.
- Ожидание сохранения на диск от одного слова SaveGame.
- Отсутствие runtime-проверки необязательной объектной привязки.

После изменений отражаемой структуры класса безопаснее закрыть редактор и выполнить обычную сборку, затем открыть его заново, чем полагаться только на Live Coding для изменений UPROPERTY.

### Как найти редкий ключ

В локальных исходниках искать точное имя и затем потребителя:

- Спецификатор: обработчик `...Specifier` в UHT.
- Meta: `GetMetaData`, `HasMetaData`, `GetBoolMetaData` и константы имени ключа.
- Числовые ограничения: NumericPropertyParams и стандартный numeric editor.
- Условия: EditConditionParser и его тесты.
- Привязки UMG: WidgetBlueprintCompiler.

Имя в справочнике — начало поиска, не гарантия для любого типа поля. Для плагина дополнительно читать его собственный customization/компилятор.

## Вывод

`UPROPERTY` — контракт поля с Unreal, а не готовая игровая логика. `Edit*`/`Visible*` управляют Details; `BlueprintRead*` — графом; Transient/Config/SaveGame — соответствующими механизмами хранения; meta — поведением поддерживающих их инструментов.

Для простого настраиваемого UI обычно достаточно `EditDefaultsOnly`, разумных числовых границ и единиц, `FText` для сообщения и `BindWidget` для визуальных элементов. Условия делают настройки удобнее, но не отменяют проверки при использовании значения.
